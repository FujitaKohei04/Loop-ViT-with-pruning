## 0. 要約

**結論：提案したサイクル型（V / W）のマルチグリッドループは、同じ計算量の bViT に勝てなかった。** 学習前の予測は外れた。

- bViT は「パラメータは減るが FLOPs は減らない」ので、同じ 1 ブロックを粗いトークン格子（4×4）にも適用して計算量を減らす構造を実装し、CIFAR-100・bViT-S・300 エポックで 9 本学習した。
- 同じ FLOPs（1.43 GFLOPs、bViT-S 12 ステップの半分）での top-1：

  | bViT-S 6 ステップ | 細→粗（4F→8C） | W サイクル | V サイクル | 粗→細（8C→4F） |
  |---|---|---|---|---|
  | 68.41% | 68.40% | 66.37% | 65.85% | 51.18% |

- 細かい格子から粗い格子へ**一度だけ降りる**構造は bViT と同等だった。粗い格子から細かい格子へ**戻る**構造は、戻る回数が多いほど悪くなった（W を深くした 25 ステップ版は 64.16%）。
- そもそも bViT-S は、この設定では 6 ステップで 12 ステップとほぼ同じ精度（68.41% 対 68.75%）が出る。ステップを半分にするだけで FLOPs は半分になるので、粗い格子を使う利点が出る余地が小さかった。
- 副産物として、**2 ブロックを交互に 3 回使う bViT（6 ステップ、3.6M パラメータ）が 69.77%** で、1 ブロック 12 ステップの bViT-S（68.75%）を FLOPs 半分で上回った。
- すべて 1 seed の結果である。0.5 pt 未満の差（68.41 と 68.40 など）は誤差と区別できない。

## 1. 調査：ループ構造をもつ ViT の現状（2026-11 時点）

前回挙げたアイデア（多重周期ループ、解像度が変わるループ、外側ループによる重みの書き換えなど）について、すでに誰かがやっていないかを Web で調べた。数値は各論文の報告値で、こちらでは再現していない。

| 研究 | 内容 | 前回のアイデアとの関係 |
|---|---|---|
| [bViT](https://arxiv.org/abs/2605.10661) (2026-05) | 1 ブロックを 12 回適用。ImageNet-1K で ViT-B とほぼ同精度、パラメータは約 1/10。FLOPs は ViT と同じ | 本リポジトリのベースライン |
| [Training Crossroads for Recurrent ViTs](https://www.alphaxiv.org/abs/2608.04879) (2026-08) | CIFAR-100 で「ブロック数 D × 反復回数 S」の格子を比較。**FLOPs を揃えると普通の ViT が勝ち、パラメータを揃えると bViT が勝つ**。12 ステップで 65.8%、60 ステップで 68.2% | 案②（ループ順序の探索）はほぼ調べられている |
| [Block-Recurrent Dynamics / Raptor](https://arxiv.org/abs/2512.19941) (ICLR 2026) | 学習済み ViT は少数のブロックの繰り返しで書き直せる（2 ブロックで DINOv2 の 96%） | ブロックを 2〜3 個に増やす方向は既出 |
| [reViT: Depth-Programmed Experts](https://arxiv.org/abs/2610.12448) (2026-10) | ステップ番号から FFN の重みを合成する。S/16 で 78.2%（DeiT III 79.9%）、パラメータ 6.1M | 案④（外側ループが内側の重みを書き換える）にかなり近い |
| Vision-MoR, Edge-RecViT (2026) | パッチごと・トークンごとに反復回数を変える | 案⑦（並列・可変回数）は既出 |
| [HRM を画像分類に適用](https://arxiv.org/abs/2510.03598) (2025-10) | 速い下位モジュールと遅い上位モジュールの入れ子。拡張なしの CIFAR-100 で 29.7% と低い | 案①（解像度を変えない二重ループ）は、そのままでは効かない可能性が高い |
| [SReT](https://arxiv.org/abs/2111.05297) (2021)、[MergeOver](https://arxiv.org/abs/2608.13141) (2026-08) | ピラミッド構造の各ステージ内で再帰。重みはステージごとに別。MergeOver は学習後にトークンを併合 | 解像度と再帰の組み合わせだが、解像度をまたぐ重み共有はない |
| [SpiralFormer](https://arxiv.org/abs/2602.11698) (2026-02) | **言語モデル**。共有ブロックを「粗い系列 → 細かい系列」の順に適用し、結果を元の系列への更新として足す。FLOPs を 3〜11% 削減。順序は粗→細と細→粗だけを比較 | 案③に最も近い。ただし画像ではなく、解像度は一方向にしか動かない |
| [LoopVAE](https://arxiv.org/abs/2609.11516) (2026-09) | 画像の VAE。共有コアを 3 つの解像度で使う。解像度の切り替え部分は別の重み。分類の実験はない | 案③に近いが、タスクが再構成で、解像度は一方向 |

調べた範囲でわかったこと：

1. 「同じブロックを繰り返す」だけの構造は 2026 年に入って急速に調べ尽くされつつある。ブロック数・ステップ数・ステップ依存の重みは、どれも既存研究がある。
2. bViT 系の弱点は **FLOPs が減らないこと**である。パラメータは 1/10 になるが、計算量は ViT と同じで、FLOPs を揃えると ViT に負ける（Training Crossroads）。
3. 「ループの中で解像度を変える」研究は SpiralFormer（言語）と LoopVAE（VAE）だけで、**画像分類では見つからなかった**。どちらも解像度は一方向にしか動かず、**解像度を何度も行き来する（ループを入れ子にする）構造は見つからなかった**。

## 2. 提案：マルチグリッド型ループ

### 2.1 着想

数値計算のマルチグリッド法は、偏微分方程式を「細かい格子で少し反復 → 粗い格子に移して反復 → 結果を細かい格子に戻して補正」という手順で解く。粗い格子の反復は安く、しかも大域的な誤差を速く減らせる。格子の行き来の仕方に V サイクル（1 往復）と W サイクル（粗い側を何度も往復）がある。

これを bViT に当てはめる。

- 細かい格子 = 8×8 のパッチトークン（F）、粗い格子 = それを 2×2 で平均した 4×4 のトークン（C）。
- **同じ 1 つのブロックを、どちらの格子にも適用する**。ブロックはトークン数によらず動くので、追加の重みは要らない。
- 粗い格子のステップはトークン数が約 1/4 なので、計算量も約 1/4 で済む。
- W サイクルは「（F を 1 回、C を 2 回）を 4 回繰り返す」という**ループのループ**になる。ユーザーの「二重ループ」の発想に、内側ループを安くする理由を与えたものと言える。脳波の θ-γ 結合（遅いリズムの中に速いリズムが入れ子になる）や HRM の「遅い上位・速い下位」とも同じ形だが、ここでは速い側を粗い解像度に割り当てている。

![各ステップがどの格子で動くか](figures/schedules.png)

### 2.2 格子間の移動

| 操作 | 式 | 学習パラメータ |
|---|---|---|
| 制限（F → C） | パッチトークンを 2×2 で平均。CLS はそのまま。その後にレベル埋め込み `e` を足す：`c0 = R(x) + e` | `e`（384 次元、ゼロ初期化）のみ |
| 粗い格子での反復 | `c = Block(...Block(c0))` | 共有ブロック |
| 補間と補正（C → F） | `x ← x + P(c − c0)`。`P` は粗いトークンを 2×2 の子トークンにコピーする。CLS の差分はそのまま足す | なし |

補正が `c − c0`（粗い格子での**更新分だけ**）になっているのがマルチグリッドの「粗格子補正」に当たる。細かいトークンは細部の情報を保ったまま、粗い格子で計算した更新だけを受け取る。平均してコピーし直す方式（`x ← P(c)`）だと、粗い格子に降りるたびに細部が消えてしまう。

### 2.3 既存研究との違い

| | SpiralFormer | LoopVAE | SReT | 本提案 |
|---|---|---|---|---|
| 対象 | 言語モデル | 画像 VAE | 画像分類 | 画像分類 |
| 解像度をまたぐ重み共有 | あり | コアのみ | なし | あり（全部） |
| 解像度の動き | 粗→細の一方向 | 一方向 | 細→粗の一方向 | **何度も往復（V / W サイクル）** |
| 格子間の移動 | 学習するルーター（反復ごとに別の重み） | 畳み込み（別の重み） | 畳み込み（別の重み） | 平均とコピー（重みなし） |

新しいと言える点は、(a) 単一ブロック再帰 ViT の画像分類に多重解像度の再帰を入れたこと、(b) 解像度を往復するサイクル型・入れ子型のスケジュールを比較すること、(c) 重みを増やさない粗格子補正の形にしたこと、の 3 つである。ただし SpiralFormer の「粗い系列で計算して更新として足す」という考え方とは共通しており、完全に新しい原理ではない。また調査は Web 検索の範囲に限られる。

### 3.2 使い方

`levels` は、各ステップをどの格子で実行するかを、`loop` と同じ文法で書く（0 = 8×8、1 = 4×4、2 = 2×2）。ステップ数は `loop` と一致させる。

```bash
# W サイクル: (F, C, C) を 4 回
uv run python train_bvit.py --model bvit_s --loop "0x12" --levels "(0,1,1)x4" --dataset cifar100
# V サイクル: F2 回、C8 回、F2 回
uv run python train_bvit.py --model bvit_s --loop "0x12" --levels "0x2,1x8,0x2" --dataset cifar100
# 実験一式
uv run python mgloop_experiments.py run
uv run python mgloop_report.py
```

### 3.3 中心部分のコード

```python
def restrict(self, x, level):            # level -> level + 1
    size = self.grid_size >> level
    prefix, patches = x[:, :self.num_prefix_tokens], x[:, self.num_prefix_tokens:]
    B, _, C = patches.shape
    patches = patches.view(B, size // 2, 2, size // 2, 2, C).mean(dim=(2, 4))   # 2x2 平均
    x = torch.cat((prefix, patches.reshape(B, -1, C)), dim=1)
    return x + self.level_embed[level] if self.level_embed is not None else x

def prolong(self, delta, level):         # level + 1 -> level
    size = self.grid_size >> (level + 1)
    prefix, patches = delta[:, :self.num_prefix_tokens], delta[:, self.num_prefix_tokens:]
    B, _, C = patches.shape
    patches = patches.view(B, size, 1, size, 1, C).expand(B, size, 2, size, 2, C)  # 子トークンへコピー
    return torch.cat((prefix, patches.reshape(B, -1, C)), dim=1)

# forward_features 内。saved は「上の格子のトークン」と「降りた直後の粗いトークン」の組を積む
def move_to(target):
    while level < target:                       # 降りる
        coarse = self.restrict(x, level)
        saved.append((x, coarse)); x, level = coarse, level + 1
    while level > target:                       # 上がる：粗格子補正
        fine, coarse_before = saved.pop()
        x, level = fine + self.prolong(x - coarse_before, level - 1), level - 1

for step in steps:
    move_to(self.step_levels[step.global_step])
    x = self.blocks[step.block_id](x)
move_to(0)
```

分類ヘッドは CLS トークンを読む。CLS はどの格子でも同じトークンとして持ち回るので、粗い格子で終わるスケジュール（W サイクル）でもそのまま分類できる。

## 4. 実験設定

- モデル：bViT-S（幅 384、6 ヘッド、共有ブロック 1 個、パッチ 4、CIFAR-100 で 64 + 1 トークン）
- 学習：[train_bvit.py](../../train_bvit.py) のデフォルト（bViT 論文のレシピ）。300 エポック、AdamW、lr 5e-4、実効バッチ 1024、Mixup / CutMix、EMA、seed 42。既存の bViT-S・ViT-S の run と同じ設定。詳細は [paper_vs_experiment_settings.md](../bvit/paper_vs_experiment_settings.md)
- 評価：最終エポックの EMA モデルの CIFAR-100 テスト top-1（`final_eval.json`）
- GPU：RTX 2080 Ti 1 枚。FLOPs は `torch.utils.flop_counter`（注意機構の行列積を含む）

| 実験名 | levels | ステップ構成 | 目的 |
|---|---|---|---|
| `vit_s`（既存） | - | 12 ブロック × 1 | 重み共有なしの上限の目安 |
| `bvit_12`（既存） | - | 12F | bViT 論文のモデル |
| `bvit_6` | - | 6F | **FLOPs を半分にした bViT**。下の 4 つと同じ FLOPs の比較対象 |

| `coarse_to_fine` | `1x8,0x4` | 8C → 4F | SpiralFormer と同じ向き |
| `v_cycle` | `0x2,1x8,0x2` | 2F, 8C, 2F | V サイクル |
| `w_cycle` | `(0,1,1)x4` | (1F, 2C) × 4 | W サイクル（ループのループ） |

| `bvit_2block_6`（追加） | - | 2 ブロックを交互に 3 回（6F） | `w_cycle_2block` と同じ FLOPs・パラメータ数の比較対象 |

4F + 8C の 4 つは、ステップの内訳も FLOPs もパラメータ数も同じで、**順序だけが違う**。

「追加」の 3 つは、最初の 2 本（`w_cycle`、`bvit_6`）の結果を見てから原因の切り分けのために足した。「未実施」の 2 つは、W サイクル自体が bViT に負けたので優先度を下げ、今回は学習していない（定義は `mgloop_experiments.py` に残してある）。

## 5. 学習前の予測

学習を始める前（2026-11-10）に書いた予測。根拠は次のとおり。

- 既存の結果：bViT-S 12F は 68.75%、ViT-S は 73.26%。bViT-S の途中ステップで打ち切った精度は、6 ステップ目 54%、9 ステップ目 68% で、後半は伸びが小さい。
- Training Crossroads では、ステップを 12 → 60 に増やしても +2.4 pt しか伸びない。逆に言えば、ステップを減らしたときの低下も緩やかなはずである。
- 粗いステップは 16 トークンしか見ないので、F のステップ 1 回分の働きはしないと考える。一方、CIFAR をスクラッチ学習する ViT は帰納バイアスが足りないので、多重スケール処理は有利に働く可能性がある。

| 実験 | GFLOPs（bViT-S 12F 比） | 予測 top-1 | 予測の理由 |
|---|---|---|---|
| `bvit_6` | 50% | 66.0 ± 1.0 | 12F から 6 ステップ減る。6 ステップで学習し直せば打ち切り精度（54%）よりずっと高いが、12F には届かない |
| `coarse_to_fine` | 50% | 65.0 ± 1.5 | 最初の 8 ステップが、生のパッチ埋め込みを平均しただけの入力で動く。局所特徴を作る前に粗くするので不利 |
| `fine_to_coarse` | 50% | 66.5 ± 1.0 | F で局所特徴を作ってから C で大域的に処理する。`bvit_6` より少し良い |
| `v_cycle` | 50% | 67.0 ± 1.0 | 最後に F へ戻るので、CLS が細部をもう一度参照できる |
| `w_cycle` | 50% | 67.5 ± 1.0 | F と C の情報交換が 4 回ある。4 つの順序の中で最良と予想 |
| `w_cycle_no_level_embed` | 50% | 67.0 ± 1.0 | 埋め込みがなくてもトークン数で格子を区別できるので、差は小さい |
| `w_cycle_3level` | 43% | 66.5 ± 1.5 | 2×2 の格子は情報が少なすぎ、8 ステップ分の価値は薄い |
| `w_cycle_deep` | 97% | 69.5 ± 1.0 | 12F と同じ FLOPs で 25 ステップ。12F（68.75%）を上回ると予想 |

まとめると、**「同じ FLOPs なら、W サイクルは bViT より 1〜1.5 pt 高い」**、**「順序は W > V > 細→粗 > 粗→細」**というのが予測である。1 seed の実験なので、0.5 pt 未満の差は誤差と区別できない点に注意する。

| bViT-S 2 blocks, 6F | 6F | - | 3.63 | 1.42 (50%) | 17,122 | 4,495 | 69.77 | 90.56 |

![精度と計算量](figures/accuracy_vs_flops.png)

灰色の破線が bViT-S（4・6・12 ステップ）で、青がマルチグリッドループである。破線より上に出た青い点はない。細→粗（4F→8C）だけが破線上（bViT-S 6F と重なる位置）にある。

### 6.2 同じ計算量で順序だけを変えた比較

![順序の比較](figures/schedule_order.png)

- 4 つのマルチグリッドモデルは、F が 4 回・C が 8 回という内訳も、パラメータも FLOPs も同じである。違いは順序だけだが、精度は 51.18%〜68.40% と 17 pt 開いた。
- 順位は 細→粗 ＞ W ＞ V ＞ 粗→細 で、予測（W ＞ V ＞ 細→粗 ＞ 粗→細）とは W・V と細→粗の位置が逆だった。

### 6.3 粗いステップは役に立っているか

| モデル | 構成 | GFLOPs | Top-1 |
|---|---|---|---|
| bViT-S 4F | 4F | 0.95 | 67.39% |
| MG 4F→8C | 4F のあとに 8C | 1.43 | 68.40% |
| bViT-S 6F | 4F のあとに 2F | 1.42 | 68.41% |

4F に C を 8 回足すと +1.0 pt、F を 2 回足しても +1.0 pt で、どちらも増える FLOPs はほぼ同じである。つまり粗いステップは無駄ではないが、**同じ FLOPs の細かいステップと同じだけしか効かない**。しかも実測のスループットは 4F→8C のほうが 10〜20% 低い（推論 15,615 対 17,240 img/s、学習 3,613 対 4,457 img/s）。小さな演算を 12 回行うほうが、大きな演算を 6 回行うより GPU の効率が悪いためで、実用上は bViT-S 6F のほうが良い。

### 6.4 途中で打ち切ったときの精度

![ステップごとの精度](figures/accuracy_per_step.png)

各ステップの直後に分類ヘッドを当てたときの精度を、そこまでに使った FLOPs に対して描いた。塗りつぶしの点が F、白抜きの点が C のステップである。

- V サイクルは、粗い格子の 8 ステップで 66.0% まで上がるが、細かい格子に戻ってからの 2 ステップでは 65.9% のままで、まったく伸びない。
- 細→粗は、粗い格子に降りた後も bViT-S 6F とほぼ同じ曲線をたどる。

### 6.5 学習曲線

![学習曲線](figures/training_curves.png)

細→粗は学習の全期間で bViT-S 6F と重なる。W サイクルと粗→細は序盤から差がつき、最後まで縮まらない。学習が足りないのではなく、構造の差である。

### 6.6 ブロックを 2 個にした場合

| モデル | Params | GFLOPs | Top-1 |
|---|---|---|---|
| MG W サイクル（1 ブロック） | 1.86M | 1.43 | 66.37% |
| MG W サイクル（F 用と C 用の 2 ブロック） | 3.63M | 1.43 | 66.97% |
| bViT-S 2 ブロック交互、6F | 3.63M | 1.42 | 69.77% |
| bViT-S 1 ブロック、12F（参考） | 1.86M | 2.84 | 68.75% |

C に専用のブロックを与えても +0.6 pt しか伸びず、同じ条件の 2 ブロック bViT に 2.8 pt 負ける。「1 つのブロックが 2 つの解像度を兼ねるのが負担」という仮説では、W サイクルの不振は説明できない。

### 6.7 予測との照合

| 実験 | 予測 | 結果 | 判定 |
|---|---|---|---|
| `bvit_6` | 66.0 ± 1.0 | 68.41 | 外れ（過小評価） |
| `coarse_to_fine` | 65.0 ± 1.5 | 51.18 | 大きく外れ |
| `fine_to_coarse` | 66.5 ± 1.0 | 68.40 | 外れ（過小評価） |
| `v_cycle` | 67.0 ± 1.0 | 65.85 | 外れ |
| `w_cycle` | 67.5 ± 1.0 | 66.37 | わずかに範囲外 |
| `w_cycle_deep` | 69.5 ± 1.0 | 64.16 | 大きく外れ |

範囲内に入った予測は 1 つもなかった。外した原因は 2 つある。(1) bViT-S がステップを半分にしてもほとんど落ちないことを見込めなかった。(2) 粗い格子から細かい格子へ戻る操作が害になることを見込めなかった。

## 7. 考察

### 7.1 なぜ「戻る」と悪くなるのか

学習済みモデルに検証画像 1000 枚を通し、粗い格子から細かい格子へ戻る瞬間の状態を測った（[mgloop_diagnose.py](../../mgloop_diagnose.py)、`outputs/mgloop/transfer_diagnosis.json`）。

- 更新 / 細：粗い格子から届く更新のノルムを、保存してあった細かいトークンのノルムで割った値
- 兄弟の類似度：同じ親をもつ 2×2 の 4 トークン間のコサイン類似度の平均。1 に近いほど 4 つが同じになり、8×8 の格子が実質 4×4 になっている

| モデル | 戻る位置 | 更新 / 細 | 兄弟の類似度（戻る前 → 後） |
|---|---|---|---|
| 粗→細 | ステップ 9 の前 | 24.5 | 0.47 → 0.999 |
| V サイクル | ステップ 11 の前 | 1.80 | 0.49 → 0.84 |
| W サイクル | ステップ 4 / 7 / 10 の前 | 0.68 / 0.57 / 0.47 | 0.80 → 0.55、0.62 → 0.51、0.50 → 0.55 |
| W サイクル deep | ステップ 5 〜 25 の前（6 回） | 0.81 → 0.22 | 0.60 → 0.59 から 0.86 → 0.89 へ |

- **粗→細**：粗い格子で 8 ステップ進めた更新が、まだ何も処理していない細かいトークンの 24 倍の大きさになる。足し合わせると 4 つの兄弟トークンがほぼ同一（0.999）になり、その後の F の 4 ステップは実質 4×4 の画像を見ている。51% という精度はこれで説明がつく。
- **V サイクル**：同じことが弱く起きている（1.8 倍、0.84）。6.4 節で「戻ってからの 2 ステップが何も足さない」ことと合う。
- **W サイクル**：更新は細かいトークンより小さく、兄弟が潰れているわけでもない。この指標では W サイクルの不振を説明できない。考えられる理由は、F のステップが 1 回ずつ途切れ途切れにしか入らず、細かい格子での連続した処理（bViT-S 6F では最初の 4 ステップで 61% まで上がる）ができないことだが、これは今回の実験では確かめていない。
- **W サイクル deep**：サイクルを重ねるごとに兄弟の類似度が上がっていく（0.59 → 0.89）。粗い更新を 6 回足すうちに細かい格子がだんだん粗くなっており、W サイクル（66.37%）より悪い 64.16% になったことと合う。

原因は「粗格子補正の大きさを制御していないこと」にあると考える。数値計算のマルチグリッドでは、粗い格子が扱うのは誤差の滑らかな成分だけだが、ここでは粗い格子のブロックが表現全体を何ステップ分も書き換え、それを 4 つの子にそのままコピーしている。

### 7.2 なぜ細→粗は害がないのか

細→粗では、粗い格子に降りた後は CLS トークンだけが分類に使われ、細かいトークンには戻らない。上の問題が起きないので、粗いステップの寄与がそのまま出る。ただし 6.3 節のとおり、その寄与は同じ FLOPs の細かいステップと同じである。CIFAR-100 の 8×8 トークンでは、4 ステップ処理した後の情報は 4×4 に平均しても失われにくい一方、粗くしたことによる利点（大域的な処理が速く進むなど）も特に出ていない、と読める。

### 7.3 bViT はステップを減らしても落ちない

今回いちばん効いた事実は、bViT-S が 12 → 6 → 4 ステップで 68.75 → 68.41 → 67.39% としか落ちないことである。Training Crossroads の「60 ステップにしても +2.4 pt」と同じ傾向で、この規模の bViT は少ないステップで飽和する。**bViT の FLOPs を減らすいちばん簡単な方法は、ステップを減らすこと**であり、新しい構造はこの基準を超える必要がある。学習前にこの基準線を測っておくべきだった。

### 7.4 2 ブロック交互の bViT

`bvit_2block_6`（2 ブロックを A B A B A B と使う）は 69.77% で、1 ブロック 12 ステップ（68.75%）より 1.0 pt 高く、FLOPs は半分、パラメータは約 2 倍（3.63M）である。bViT 論文の Table 3 や Raptor の「2〜3 ブロックの再帰で十分」という結果と同じ方向で、CIFAR-100 のスクラッチ学習でも成り立つことが確認できた。1 seed なので差の大きさは確定ではないが、枝刈りの対象としては 1 ブロックの bViT より良い出発点かもしれない。

## 8. 限界と次の一手

### 8.1 限界

- **1 seed・1 データセット・1 モデルサイズ**である。0.5 pt 未満の差は判定できない。「V / W サイクルが bViT に 2 pt 以上負ける」「粗→細が大きく崩れる」は差が大きいので信頼できるが、「細→粗が bViT-S 6F と同等」は「差が見えなかった」という意味である。
- CIFAR-100 は 32×32 で、トークンは 8×8 しかない。粗い格子は 4×4 = 16 トークンで、解像度を落とす余地が小さい。ImageNet（14×14 → 7×7）では結果が変わる可能性がある。
- bViT 論文によれば、幅の狭いモデルほど再帰の損失が大きい。bViT-B（幅 768）では試していない。
- 格子間の移動は、重みなしの平均とコピーの 1 種類しか試していない。レベル埋め込みのアブレーションと 3 段格子は未実施である。
- 学習率などは bViT 用の値をそのまま使った。マルチグリッド側に合わせた調整はしていない。

### 8.2 次に試す価値があること

優先度の高い順に挙げる。

1. **戻るときの更新を制御する**。7.1 節の診断から、まず試すべきはこれである。候補は、(a) 更新に学習可能な係数（ゼロまたは小さい値で初期化）を掛ける、(b) 更新を正規化してから足す、(c) コピーではなく、細かいトークン自身の特徴で 4 つの子に配り分ける（SpiralFormer のルーターに近い）。`prolong()` の数行の変更で済み、V サイクル 1 本（約 1.4 時間）で効果を確かめられる。
2. **2 ブロック交互の bViT を枝刈りの対象にする**。今回いちばん成績が良かった軽量モデルで、本リポジトリの枝刈り研究に直接つながる。まず seed を変えて 69.77% を再現する。
3. **細→粗を「途中からトークンを減らす bViT」として詰める**。同精度・同 FLOPs なので現状は利点がないが、降りる位置（2F→、3F→）や、より粗い格子（2×2）を使えば、bViT の精度と FLOPs の曲線の下側（0.95 GFLOPs 以下）を改善できる可能性がある。bViT-S 4F（67.39%）が基準になる。
4. **解像度の高いデータで再検証する**。ImageNet-100（224px、14×14 トークン）なら粗い格子に十分な情報が残る。ただし 1 本あたりの学習時間は大幅に増える。

### 8.3 再現方法

```bash
uv run python mgloop_experiments.py list     # 実験の一覧と完了状況
uv run python mgloop_experiments.py run      # 未完了の実験を順に学習（完了済みは飛ばす）
uv run python mgloop_report.py               # 表と図を作り直す（スループット測定に GPU を使う）
uv run python mgloop_diagnose.py             # 7.1 節の診断
```

学習時間の実績（RTX 2080 Ti、300 エポック）：bViT-S 4F が約 45 分、6F が約 1 時間、4F + 8C のモデルが約 1.4 時間、W サイクル deep が約 2.7 時間。
